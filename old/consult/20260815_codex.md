## 2. Executive assessment

The central architecture is sound: keep user-authored reactive logic in a small interpreted language, keep heavy computation in compiled Rust/WASM, and mediate graph, network, model, device, and extension effects through QualiaDB/Webizen. VibeScript can become a distinctive semantic application language rather than a general-purpose JavaScript replacement.

The present documents are best described as an architectural concept plus an illustrative syntax. They are not yet an implementable or testable language standard. The grammar rejects several of its own examples, key runtime semantics are absent, the security model is too implicit, the QApp execution boundary is contradictory, RDF 1.2 syntax is misidentified, and several file-format/runtime statements do not match the current code.

The most important architectural recommendation is:

> Keep the VibeScript language core small, typed, deterministic, bounded, and stable. Expose QualiaDB through a generated, versioned capability-binding layer. Do not turn thousands of evolving Rust functions or 124 VM opcodes into grammar productions or permanent keywords.

This yields both breadth and stability. New geometry, logic, audio, vision, inference, clinical, or networking operations become typed capability descriptors and standard-library functions without changing the parser.

### What should be retained

- The Poet engine / VibeScript language naming split.
- The three-tier separation between workbench UI, interpreted orchestration, and compiled compute.
- First-class semantic values rather than stringly typed graph calls.
- No JIT requirement for the core language.
- Rust/WASM implementation, explicit runtime profiles, structured diagnostics, golden corpora, and machine-readable language metadata.
- `pulse` as the transport/event concept and `aura` as the ontology/semantic concept.
- Code provenance, signed packages, bounded execution, and an optional graph representation of code.

### What must change before a v1.0 label

| Priority | Blocking issue | Required decision or artifact |
|---|---|---|
| P0 | Grammar and examples disagree | One executable grammar source; regenerate the published EBNF and validate every example in CI. |
| P0 | No normative type/effect model | Define values, ownership/handles, errors, effects, async jobs, streams, and profile availability. |
| P0 | QApp declares “no executable logic” while HCF embeds effectful scripts | Preserve declarative QApps; reference separately signed Vibe modules and permit only pure inline formulas by default. |
| P0 | NQuin syntax misrepresents the 48-byte ABI | Specify a typed Quin API and resolve current parity/sensitivity/tag inconsistencies before exposing raw layout. |
| P0 | Security is described but not part of program semantics | Add declared capabilities, effect checking, sensitivity/consent gates, transactions, receipts, and no ambient authority. |
| P0 | Capability coverage is hand-written and incomplete | Generate Vibe bindings and documentation from a universal Qualia capability manifest. |
| P0 | Runtime determinism and reactivity are unspecified | Define snapshots, dependency tracking, event ordering, cycles, retry/idempotency, cancellation, and commit atomicity. |
| P1 | Bytecode, graph AST, and package formats are conflated | Specify source, canonical AST, executable bytecode, debug map, manifest, and signatures as distinct artifacts. |
| P1 | Platform claims are broader than compiled profiles | Make target-profile checking mandatory and distinguish current, partial, experimental, and planned surfaces. |
| P1 | RDF/CBOR-LD/HMC/10D statements are inaccurate or unversioned | Pin standards versions and align the docs with implemented formats or clearly mark roadmap proposals. |
| P1 | Agent-readiness promises only syntax validity | Generate grammar constraints, typed AST schema, semantic diagnostics, negative cases, and execution-policy tests from the same source. |

## 3. Define the specification as a family of normative documents

The current single language document mixes vision, grammar, backend inventory, UI conventions, mobile strategy, file formats, and product examples. Split it into versioned layers:

1. **Vibe Core Language** — lexical grammar, syntax, static types, control flow, errors, modules, functions, evaluation, and determinism.
2. **Poet Abstract Machine** — bytecode, verifier, stack/frame limits, scheduling, gas, cancellation, and diagnostics.
3. **Qualia Binding Profile** — typed standard-library namespaces and capability descriptors.
4. **Security and Effects Profile** — authority, sensitivity, consent, delegation, audit, transactions, external effects, and receipts.
5. **Reactive/HCF Profile** — cells, dependency graphs, component events, graph subscriptions, and QApp integration.
6. **Packaging and Interchange** — source, AST graph, CBOR-LD representation, bytecode, manifest, hashes, signatures, and version negotiation.
7. **Runtime Profiles** — native, browser portal, ontology, logic, scientific, LLM/full, mobile, and genuinely `no_std`/edge subsets.
8. **WASM Component Profile** — WIT interfaces/worlds, guest imports/exports, component signatures, and host adapters.
9. **Conformance** — positive/negative syntax tests, semantic tests, profile tests, security tests, deterministic replay, fuzzing, and compatibility fixtures.

Use RFC-style normative language (`MUST`, `MUST NOT`, `SHOULD`) only in normative sections. Mark product vision and examples as non-normative. Version the core language separately from the standard library and from each runtime capability profile.

There should be one machine-readable source of truth for tokens, grammar, AST nodes, types, built-ins, error codes, and capability metadata. Generate the Markdown EBNF, GBNF, typed AST schema, syntax highlighting, formatter tables, agent ontology, API reference, and portions of the conformance suite from it. Hand-maintained mirrors will drift.

## 4. Grammar and language-core review

### 4.1 The published grammar does not accept the published examples

Concrete failures include:

- No comment production exists, but every example uses `//` comments.
- `on_event` is used but is not a valid hook name.
- Member access and method calls are absent, yet examples use `stream.read_telemetry()`, `reading.value`, `player.get_head_position()`, `camera.motor`, `actor.velocity.length()`, and `payload.surface_type`.
- General namespace calls are absent. `hmc.get_mesh`, `math.clamp`, `graph.get_node`, `graph.resolve_phonology`, and `graph.match` are not grammatical.
- Record/list literals such as `[emotion: "warm", pitch_contour: 1.05]` are not expressions. Square brackets exist only as an annotation suffix on one special graph literal.
- Query variables such as `?s` are only legal inside `PatternElement`, yet examples pass them as ordinary call arguments.
- `await graph.commit_delta(...)` cannot parse: `graph.commit_delta` is a statement-only `GraphMutation`, not a primary expression.
- Typed parameters, return types, generics, option/result types, streams, futures, handles, and bounded collections do not exist even though the runtime design requires them.
- The grammar has no modules, imports, prefix declarations, capability declarations, structured error handling, pattern matching, cancellation, transactions, or resource budgets.
- Strings have no escape rules; numbers lack exponents, bases, suffixes, width, decimal policy, and non-finite rules.
- The ASCII-only identifier/QName grammar is not compatible with the broader Turtle local-name grammar and does not state Unicode normalization policy.
- `<` is both a relational operator and the start of an IRI without a specified lexer precedence rule.
- There is no statement terminator rule for a reactive `= Expression`, and its permissible host context is undefined.

Every fenced Vibe example in the repository should be extracted and parsed in CI. Examples should never be exempt from the grammar.

### 4.2 Use a generic postfix expression grammar

Do not enumerate `graph`, `pulse`, `aura`, `anim`, `rig`, `ik`, `physics`, and every method in EBNF. That makes new Qualia capabilities a language-version change. Parse ordinary member access and calls; define namespaces and functions in the generated standard library.

An illustrative structural direction is:

```ebnf
Program        ::= ModuleDecl? ImportDecl* PrefixDecl* RequiresDecl? Item* ;
Item           ::= FunctionDecl | EventHandler | ConstDecl | Statement ;
Statement      ::= LetStmt | AssignStmt | IfStmt | ForStmt | MatchStmt
                 | ReturnStmt | YieldStmt | TransactionStmt | EffectStmt
                 | Expression ";" ;

Expression     ::= LogicalOr ;
PostfixExpr    ::= Primary (MemberAccess | Call | IndexAccess | TrySuffix)* ;
MemberAccess   ::= "." Identifier ;
Call           ::= "(" ArgumentList? ")" ;
IndexAccess    ::= "[" Expression "]" ;
TrySuffix      ::= "?" ;

Primary        ::= Literal | Identifier | QueryVariable | Iri
                 | TripleTerm | ReifiedTerm | QuinLiteral
                 | ListLiteral | RecordLiteral | TupleLiteral
                 | AwaitExpr | SpawnExpr | "(" Expression ")" ;

EventHandler   ::= "on" EventPath "(" TypedParameters? ")"
                   BudgetClause? ReturnType? Block ;
EffectStmt     ::= "effect" Expression ";" ;
TransactionStmt ::= "transaction" TransactionOptions? Block ;
```

This is not a complete replacement grammar. It demonstrates the necessary separation: syntax recognizes calls; the type checker resolves `graph.query`, `logic.deontic.evaluate`, or a future capability through versioned descriptors.

### 4.3 Required lexical and syntactic decisions

- UTF-8 source is mandatory. Define BOM and newline handling.
- Choose whether identifiers are ASCII or Unicode. If Unicode is supported, pin a normalization form and identifier-security policy. Strings still support all Unicode either way.
- Define line and nested/non-nested block comments.
- Define escapes, raw strings, byte strings, template strings, and interpolation explicitly.
- Define `i32`, `u32`, `i64`, `u64`, `f32`, `f64`, fixed decimal, quantity/unit, duration, instant, and interval literals. `Number` is too ambiguous for hashes, Lamport clocks, finance, QUDT, and GPU values.
- Define operator precedence, associativity, overflow, division-by-zero, NaN, equality, hashing, and conversion rules.
- Prefer `Result<T,E>` and `Option<T>` with `match`/`?` over exceptions and panics.
- Disallow unbounded recursion. Verify maximum call depth. Loops over streams or query results must be explicitly bounded (`take(n)`, a fixed-capacity result type, gas, or a profile limit).
- Define closures/higher-order functions only if their allocation and capture rules are clear; they are not necessary for the first release.

### 4.4 RDF 1.2 syntax must be corrected or labelled as Vibe sugar

The triple-term spelling `<<( s p o )>>` matches current RDF 1.2 Turtle. The proposed explicit-reifier form `<< id | s p o >>` does not. RDF 1.2 Turtle uses a reifying-triple form based on `<< s p o ~ reifier >>`. RDF 1.2 also gives triple terms a more constrained RDF role than a general Vibe value.

Choose one of two defensible designs:

1. Adopt exact RDF 1.2 Turtle spellings and semantics; or
2. Keep a friendlier Vibe literal, call it Vibe syntax, and normatively define its lossless lowering to RDF 1.2.

Do not describe a non-standard spelling as W3C RDF 1.2. Also define asserted versus unasserted terms, blank-node allocation, nested-term limits, canonical hashing, lexicon registration, and how a Vibe value becomes one or more NQuins.

## 5. Type, effect, resource, and execution model

### 5.1 Minimum semantic value model

The core should have explicit values rather than treating everything as `String`, `Number`, or raw `u64`:

| Type family | Required semantics |
|---|---|
| Scalars | Width-specific signed/unsigned integers, `f32`/`f64`, fixed decimal, booleans, strings, bytes, and overflow policy. |
| Semantic identifiers | `Iri`, `BlankNode`, `Did`, `Hash`, and `ContextId`; never interchange these merely because the host stores each as `u64`. |
| RDF values | `Literal`, `TripleTerm`, `Reifier`, `GraphName`, `Statement`, and typed query bindings. |
| Qualia values | Safe `Quin`, `QuinRef`, `QuinBuffer<N>`, `TensorRef`, `GeometryRef`, `AssetRef`, `ModelRef`, and `MediaRef`. |
| Time and units | `Instant`, `Duration`, `Interval`, Lamport/vector-clock types, `Quantity<Unit>`, and explicit reference frames. |
| Control values | `Option<T>`, `Result<T,E>`, tuples, records, enums, fixed/bounded lists and maps. |
| Async values | `Future<T>`, `Stream<T>`, `Subscription`, `Job<T>`, `CancelToken`, and `Receipt<T>`. |
| Authority values | Unforgeable `Capability`, `Grant`, `Consent`, `Delegation`, `Attestation`, and transaction handles. |

JavaScript `Number` cannot safely carry a Qualia `u64`. Browser bindings must use `BigInt`, decimal/hex strings, or typed byte buffers. The existing ontology WASM endpoint already serializes Quin `u64` values as strings for this reason; Vibe must make the rule universal.

Dense pixels, PCM, biometric templates, model weights, large tensors, and meshes must not be embedded in NQuins or copied through ordinary script values. Scripts receive validated content-addressed handles with generation, range, digest, lifetime, access class, and byte budget.

### 5.2 Make effects visible and statically checked

At minimum, distinguish:

- **Pure:** deterministic computation over immutable values/snapshots.
- **Hot bounded:** zero-heap evaluation over caller-owned buffers.
- **Cold bounded synchronous:** construction using a declared workspace budget.
- **Asynchronous job:** geometry builds, model inference, large transforms, provisioning, or external process work.
- **External effect:** graph commit, file/storage mutation, network publication, device access, UI mutation, model installation, credential use, or extension dispatch.

The existing QISP `ImmersiveFunctionDescriptor` is an excellent starting point: it already records typed arguments/results, `HotZeroHeap`/`ColdBoundedSync`/`AsyncRequired`, determinism, exactness, and input/output byte limits. The computational-geometry `OpManifest` adds backends, maturity, allocation class, dimensionality, topology criticality, time, memory, and output limits. Vibe should generalize these rather than create a weaker gas-only model.

An effectful function should declare its effect set, and callers should propagate it. Pure reactive cells must not acquire network, filesystem, credential, model-installation, or graph-write authority indirectly.

### 5.3 Gas is necessary but insufficient

Add independent limits for:

- instruction/step count;
- call depth and stack bytes;
- script heap and temporary workspace bytes;
- input/output bytes and collection cardinality;
- graph rows scanned and returned;
- subscriptions, queued events, and outstanding jobs;
- wall-clock/deadline and cancellation polling;
- GPU/VRAM, model residency, thermal/energy class, audio frames, and render commands;
- network destinations, request/response bytes, and rate limits.

The effective limit is the minimum of the runtime profile, capability manifest, package declaration, calling context, data sensitivity policy, and user/guardian grant. The 42 MiB SLG arena is a core constraint, not a universal permission for every script heap. Tier-1 calls must preserve caller-buffer/zero-heap contracts; Tier-2 construction must use bounded workspaces and fail closed before exceeding them.

### 5.4 Define deterministic reactivity

Specify:

- the graph snapshot/revision seen by a handler;
- dependency tracking for reactive cells;
- invalidation and recomputation order;
- cycle detection and bounded fixed-point behavior;
- ordering of UI, graph, pulse, timer, animation, and job-completion events;
- whether handler delivery is at-most-once or at-least-once;
- idempotency keys and retry behavior;
- cancellation, timeout, and shutdown semantics;
- reentrancy and whether a handler can observe its own uncommitted writes;
- deterministic tie-breaking using Lamport/context/event identifiers;
- how non-deterministic backends, time, entropy, sensors, and network inputs are recorded for replay.

`on_tick` must be a restricted real-time profile. It should use fixed-step clocks and preallocated command buffers, not arbitrary graph queries, allocation, model inference, or network commits at 60/120 Hz. Slow work becomes an async job whose completion emits a later event.

### 5.5 Graph transactions are a first-class language concept

Use snapshot-isolated transactions:

1. Read an immutable graph revision.
2. Stage typed assertions/retractions into a bounded delta.
3. Validate datatype/shape constraints.
4. Run deontic, sensitivity, consent, delegation, and capability checks.
5. Recalculate ABI metadata/parity through core constructors.
6. Atomically commit or return a structured rejection with no partial effects.
7. Emit a signed/auditable receipt and deterministic graph-change event.

Do not expose `graph.assert` as an immediate unmediated mutation. Prepared/typed queries should be preferred over dynamic SPARQL strings; dynamic strings remain an explicitly parsed capability with its own budget and error surface.

## 6. NQuin and Q42 ABI recommendations

The proposed `<<[ s p o g prov ]>>` literal is not an accurate public model of the current NQuin. The implemented structure is six `u64` fields: `subject`, `predicate`, `object`, `context`, `metadata`, and `parity`. Provenance is not simply the fifth field, and `parity` should never be authored as provenance.

### 6.1 Current ABI issues that block a raw literal

| Issue | Current evidence | Recommendation |
|---|---|---|
| Parity definition conflict | `NQuin::calculate_parity` includes metadata, while `foundation/frame_layout.rs::parity` excludes metadata and its tests require metadata-independent parity. | Resolve and version one canonical parity rule before the language standard freezes a constructor. |
| Sensitivity has two representations | `context` has a top-byte sensitivity API; metadata also has a role-specific ODRL sensitivity tier. | Expose a typed `SensitivityLabel`; let the ABI adapter choose the versioned representation. |
| Metadata is a role-keyed union | Low 32 bits and several high overlays mean different things for different Quin roles, with intentional overlaps. | Require role-specific builders; prohibit arbitrary metadata bit operations in ordinary Vibe code. |
| Embedded-term/integer tag overlap | The current resolver documents `TAG_EMBEDDED` and the integer tag sharing a pattern, with lexicon lookup taking precedence. | Keep `TripleTerm` and `Integer` distinct in the language and lower through the lexicon; never ask scripts to construct tags. |
| Predicate has two modes | Some modality Quins pack opcode/path/defeater bits; proposition-mode modalities use the whole predicate hash. | Use typed modality constructors, not one generic numeric predicate setter. |
| Hashes are handles, not complete identity | `q_hash` is compact and the lexicon is the collision backstop. | Keep canonical full IRIs/DIDs in package metadata/lexicons and expose collision-aware resolution. |

### 6.2 Recommended public surface

- `quin.statement(subject, predicate, object, context)` for an ordinary semantic statement.
- Role-specific constructors such as `logic.deontic.obligation(...)`, `logic.epistemic.belief(...)`, `tensor.node(...)`, and `vision.observation(...)`.
- Read-only typed accessors; no direct parity or raw-overlay mutation outside an explicitly unsafe/diagnostic host API.
- `quin.seal()` implemented only by `qualia-core-db` and parameterized by ABI version.
- A `FrameLayoutVersion`/engine-version handshake in packages and bytecode.
- Compile-time hashing for literal IRIs/prefixes. Dynamic identifiers go through a bounded, collision-aware lexicon/interning API outside hot loops.
- Structured provenance as a graph/receipt: source content hash, canonical UTF-8 byte span, author/principal DID, transform and version, input hashes, confidence/exactness, clock, policy/consent reference, and attestation. A free-form `ProvenanceTag` string is insufficient.

## 7. Universal Qualia capability-binding architecture

QualiaDB already has several complementary truth sources:

- `qualia_core_db::CAPABILITY_DESCRIPTORS` for 28 broad families, maturity, operations, tools, and surfaces;
- `wasm_capabilities.rs` for compile-time browser profiles;
- QISP `ImmersiveFunctionDescriptor` for typed execution/exactness/budgets;
- computational-geometry `OpManifest` for backend, maturity, exactness, allocation, dimension, and resource limits;
- honest audio and vision capability registries with `Present`, `Partial`, `Missing`, feature-disabled, or needs-weights states;
- the Webizen `SlgOpcode` instruction set and the SHACL extension compiler;
- extension manifests, renderer contracts, and separate application/runtime crates.

These should feed one generated registry rather than be independently re-described in Vibe documentation.

### 7.1 Required universal descriptor

Each callable capability should publish:

| Field | Purpose |
|---|---|
| Stable semantic ID/IRI and version | Binding and compatibility independent of Rust symbol names. |
| Typed parameters and result/error schema | Compile-time checking and agent generation. |
| Execution/effect class | Pure hot, cold bounded, async job, or external effect. |
| Allocation and resource limits | Input/output/workspace/time/cardinality/GPU/network budgets. |
| Determinism and exactness | Bit-exact, deterministic approximate with tolerances, interactive approximate, or non-deterministic with receipt. |
| Maturity and evidence | Planned/foundation/implemented/verified/done, test/oracle identifiers, and fail-closed conditions. |
| Runtime profiles and backends | Native, WASM profile, renderer, MCP, CPU/SIMD/WGPU/CUDA/QPU, required feature flags. |
| Authority and sensitivity contract | Required capabilities, maximum data classification, consent/delegation/attestation rules, permitted destinations. |
| Cancellation and transaction behavior | Polling guarantees, idempotency, rollback, and receipt type. |
| Provenance/receipt schema | Inputs, outputs, backend/device/model digests, versions, seeds, tolerances, policy verdict, and timing. |

Generate from this registry:

- Vibe standard-library stubs and type metadata;
- runtime dispatch tables and profile checks;
- WIT interfaces/worlds;
- MCP and agent tool schemas where appropriate;
- the Vibe ontology and SHACL shapes;
- API documentation, completion metadata, diagnostics, GBNF/AST constraints, and conformance cases.

Do not expose Rust enum discriminants or `SlgOpcode` layout as the public Vibe ABI. Vibe calls stable semantic operations; the engine version lowers them to current SLG/native operations. Rust enum layout is not a portable serialized contract.

### 7.2 Namespaces should express concepts, not implementation crates

Recommended top-level families are:

- `graph`, `rdf`, `query`, `aura`, and `logic`;
- `space`, `geom`, `tensor`, and `render`;
- `compute` with domain subnamespaces (`math`, `stats`, `bio`, `chem`, `clinical`, `physics`, `economics`, `engineering`, `quantum`);
- `vision`, `audio`, and `model`;
- `pulse`, `storage`, and `asset`;
- `identity`, `rights`, `governance`, and `audit`;
- `extension`, `component`, `runtime`, and `ui`.

`aura` should remain ontology/schema/context operations; `pulse` should remain event/transport. Speech synthesis belongs under `audio.speak` or `audio.synthesize`; `pulse.emit` can transport its resulting event or handle. This prevents a branding namespace from becoming an untyped miscellaneous API.

Also provide a typed `capability.resolve(id)`/`capability.invoke(...)` escape hatch for newly registered extensions. It must still enforce descriptors, profiles, effects, and authority; it is not dynamic unchecked reflection.

| Files and asset containers | Q42, P64, `.10d`, `.hmc`, CBOR-LD/YAML-LD paths, sidecars, semantic media libraries | `asset`/`storage`; content-addressed URIs, range reads, format-version checks, integrity/signature receipts, retention/cleanup budgets. |
| Extensions and WASM components | Extension bus/manifests, WASM bridge/profile exports, ontology MCP, desktop host commands | `extension`/`component`; signed manifest, typed WIT/capability imports, sandbox, no raw paths or boolean guardian bypass, job/receipt boundary. |
| Application and cooperative domains | QApp/client-core/runtime/studio/desktop/browser, semantic library, cooperative and WellFair domain crates | `ui` plus domain packages; keep domain packages optional and versioned, reuse the same capability/effect/rights system rather than adding language keywords. |

The current broad `CAPABILITY_DESCRIPTORS` registry omits or under-describes several product surfaces, notably audio, detailed inference, transport/storage, and much of rendering/application behavior. Extend the registry or create the universal registry above; otherwise “full coverage” will remain a documentation exercise rather than an enforceable contract.

## 9. Reconcile VibeScript with QApps, HCF, and the UI

### 9.1 Preserve the declarative QApp trust boundary

`docs/manuals/qapps_specification.md` says a QApp is declarative and does not contain executable heavy logic; it emits capability intents to the guarded shared pool. The HCF/Vibe documents currently embed arbitrary effectful handlers. Both cannot be normative without a boundary.

Recommended resolution:

- A QApp manifest remains declarative.
- A QApp may reference a signed Vibe package by content hash and version.
- The manifest declares the package's requested capabilities and bindings.
- The host displays and obtains grants for effects before activation.
- Inline HCF formulas are pure, read-only, bounded expressions by default.
- Effectful handlers live in separately signed modules, not anonymous document strings.
- A QApp can run without a module; a module cannot expand authority beyond the QApp/host/user grants.
- Heavy operations are submitted as intents/jobs to the capability runtime; they are not performed inside the UI interpreter loop.

Never expose `guardianship_override: bool` as script authority. The current extension-bus proof-of-architecture uses such a boolean and simulates dispatch; a production Vibe binding must require a verified, scoped, expiring credential/delegation/attestation object and must fail closed.

### 9.2 Separate the three code representations

The HCF example labels a YAML block containing raw Vibe source as a “homoiconic AST.” It is source text, not an AST. Specify three related artifacts:

1. **Source:** UTF-8 `.vibe` text for humans and diffs.
2. **Canonical AST graph:** a versioned Vibe ontology encoded as RDF/CBOR-LD/Q42 for analysis, agent generation, provenance, and interchange.
3. **Verified bytecode:** a compact execution artifact with imports, constant pool, code, limits, and debug spans.

Record explicit edges and hashes: `source --parsesTo--> AST --lowersTo--> bytecode`. Sign the package manifest and the hashes of all three when present. Binary AST still requires decoding, validation, import resolution, and verification; describe it as avoiding source lexing, not “zero runtime overhead.”

### 9.3 Define a semantic component tree, not a contradictory DOM promise

HCF can define `<q-doc>`-like semantic component concepts without requiring HTML to be canonical. Specify:

- a virtual, typed component tree in HCF;
- a deterministic projection to Web Components/DOM in browser hosts;
- native renderer projections that need no DOM;
- stable typed event schemas independent of `CustomEvent` payload conventions;
- byte-span/source anchors and edit transformations;
- lifecycle, focus, accessibility, localization, and error behavior;
- the legacy `www/` frame as a separately sandboxed compatibility surface.

For source anchoring, make UTF-8 byte offsets canonical because core parsers and cryptographic hashes operate on bytes. Optional Unicode-scalar and grapheme-cluster positions may be derived. Store source-content hash, normalization policy, and edit/rebase provenance so an annotation cannot silently point at changed text.

## 10. Standards, formats, and implementation-honesty corrections

| Current statement | Finding | Required correction |
|---|---|---|
| Vibe explicit reifier `<< id \| s p o >>` is W3C RDF 1.2 | Current Turtle 1.2 uses a different explicit-reifier spelling. | Adopt the standard spelling or call the Vibe form syntactic sugar and specify lowering. |
| CBOR-LD 1.0 is treated as a finished fixed standard | CBOR-LD 1.0 is currently a W3C Working Draft dated 2026-05-11. | Pin the draft date/version and define a compatibility/migration policy. |
| SPARQL/SHACL-AF/ShEx are presented as uniformly complete | Qualia has substantial SPARQL/SHACL code, but capability maturity varies; ShEx is not evidenced as a complete engine, and SHACL extension opcodes are not the same as full SHACL-AF. | Publish exact supported profiles/features and conformance results; avoid blanket “full” claims. |
| HMC embeds a Bao BLAKE3 outboard tree with a signed DID manifest | Current `.hmc` v1 is a transparent intact-file bundle with `QBDL` magic, 64-byte alignment, whole-file CRC-32C, and per-entry SHA-256. It does not currently implement the described Bao tree in the format. | Make the implemented HMC v1 normative, or design/version a future HMC v2 extension without claiming it exists. |
| The 10D extension is `.d10` | Current implementation and comments consistently use `.10d`. | Select one canonical extension; preferably align with `.10d`, document MIME/kind strings and migration aliases. |
| WGPU 29 | Current `qualia-core-db`, `webizen-render`, and `webizen-runtime` manifests use wgpu 30. | Avoid embedding library versions in language semantics; put tested implementation versions in a profile appendix. |
| `yaml-ld-q42` is a complete HCF compiler | Current compiler deserializes a narrow `WebizenWorkspace { pages, panes }` schema and allocates `Vec`/`String`; it is not a general YAML-LD/CBOR-LD/HCF compiler. | Mark current scope accurately and specify the full HCF grammar/codec as future work with conformance fixtures. |
| HMC always offers zero-copy WASM memory mapping | Native `BundleMmap` is zero-copy; WASM consumes fetched byte slices/ranges and cannot use native mmap semantics. | Define per-profile access semantics and avoid universal “mmap” language. |
| Poet has zero runtime overhead | An interpreter, verifier, dispatch layer, graph decode, and effects have overhead. | Say “no JIT/AOT wait for user scripts,” “preverified bytecode,” and “bounded/zero-heap hot paths where certified.” |
| Edge profile is `no_std`, under 2 MB, and runs stripped `qualia-core-db` | `qualia-core-db` is generally `std`; the workspace has separate profiles and a `#![no_std]` `qualia-q-forge`, but the claimed Micro-Poet/Core footprint is not established by the reviewed code. | Treat MCU/`no_std` as a separately built and measured product profile with a small certified capability set. |
| Every native machine has AVX-512/direct raw networking | Hardware and browser/mobile permissions vary. | Use capability negotiation and backend descriptors, never architecture assumptions in the language spec. |
| “Mathematically perfect” speech/lip sync and broad EMF claims | These are product/research aspirations, not language or container guarantees. | Move to non-normative vision material and require measured error/quality profiles for implemented pipelines. |

The format specification should include magic, version, endianness, alignment, integrity algorithm, canonical serialization, section/index layout, maximum sizes, unknown-section behavior, signature coverage, media types, and test vectors for every normative binary format. Marketing descriptions should not replace byte-level contracts.

## 11. Security, privacy, governance, and human authority

### 11.1 No ambient authority

Every module declares imports/capabilities such as graph scopes, network topics/destinations, asset collections, UI surfaces, devices, models, credentials, or extensions. The runtime supplies only approved imports. A pure module with no imports cannot reach a filesystem, secret store, network, clock, entropy source, sensor, graph writer, or model runtime.

For WASM packages, WIT worlds are a natural representation of this boundary: imports express dependencies and exports express callable handlers. A component lacking a secret-store or network import cannot access it. Vibe packages should use the same conceptual model even when executed by Poet bytecode rather than a WASM component.

### 11.2 Rights and sensitivity must be enforced at every crossing

Check both inputs and outputs when data crosses:

- graph snapshots and transaction commits;
- script/host, script/WASM, extension, daemon, renderer, model, network, and legacy-web boundaries;
- logging, diagnostics, cache, clipboard, export, and telemetry paths.

A data classification is not a single numeric comparison. Policy must consider principal, purpose, context, jurisdiction, consent, delegation, expiry, recipient, destination, operation, retention, onward disclosure, and derived-data classification. Derived model/vision/audio outputs inherit or strengthen restrictions unless an explicit policy proves otherwise.

### 11.3 Receipts are part of the result type

Rights-affecting or external operations return a receipt containing:

- principal/agent and authorizing grant;
- capability and version;
- policy/deontic verdict and relevant evidence hashes;
- input/output content hashes and sensitivity;
- graph revision, Lamport/event identifier, and time source;
- backend/device/model/weights, seed, exactness/tolerance, and maturity;
- resource use, cancellation/timeout, and commit/disposition;
- human attestation/override where valid.

An apology string, boolean override, console log, or mutable in-memory flag is not an audit record.

### 11.4 Model and sensor outputs are epistemic proposals

Qualia Vision and Audio already state this design rule. Carry it into Vibe's type model. `vision.detect`, `audio.classify`, `model.generate`, and biosense operations should return an `Observation`/`Proposal` with confidence, provenance, model digest, limitations, and human-correction/rejection links. They must not silently become asserted ground truth or medical/legal/financial decisions.

### 11.5 Legacy web frames

The `www/` compatibility partition needs:

- a sandbox profile that does not combine `allow-scripts` and `allow-same-origin` for untrusted same-origin content without a documented threat analysis;
- exact postMessage origin/source checks and schema validation;
- capability tokens scoped per frame and event;
- message size/rate limits and backpressure;
- no direct raw DID keys, paths, graph handles, or capability objects;
- revocation, teardown, navigation, popup/download/clipboard/storage/network policy;
- audit receipts for bridge calls.

## 12. Bytecode, packages, and WASM interoperation

### 12.1 Poet bytecode

Define a stable, non-recursive verified bytecode separate from the Webizen SLG instruction enum. A package should contain at least:

- magic and format version;
- core-language and standard-library compatibility ranges;
- target capability/profile requirements;
- constant/IRI/type/function/import tables;
- bytecode and bounded stack/frame metadata;
- source map using UTF-8 byte spans;
- declared budgets/effects;
- canonical AST/source hashes;
- dependency/content hashes;
- signer/provenance and signature coverage.

The verifier must reject unknown required features, invalid control flow, recursion/depth violations, type errors, buffer overflows, illegal effect calls, unsupported profiles, or undeclared capability imports before execution. Unknown optional imports may activate an explicit fallback branch; they must not silently degrade semantics.

### 12.2 WASM packages

Use the WebAssembly Component Model/WIT as the preferred typed package contract, while recognizing that host/toolchain support varies by profile. Define Qualia-specific WIT interfaces for graph snapshots/transactions, bounded buffers/assets, jobs/streams, capability discovery, receipts, and cancellation. Browser deployments may initially use generated core-WASM/`wasm-bindgen` adapters while preserving the same semantic contract.

WASM guests must not receive raw process pointers or arbitrary host paths. Use validated resource handles. The host decides which imports are linked, enforces fuel/memory/table limits, validates components/signatures, and records effects. Dynamic WASM support on iOS/mobile must be a separately verified profile; do not infer App Store compliance merely from the Poet interpreter being JIT-free.

## 13. AI-agent readiness and developer tooling

The AI-agent requirements are directionally good, but grammar-constrained decoding cannot guarantee semantic validity or safe execution. “100% syntactically valid” is only meaningful for a specific generated grammar and still says nothing about types, capabilities, profile availability, effects, authority, resource bounds, or runtime errors.

Recommended toolchain:

- reference lexer/parser with lossless syntax tree and error recovery;
- formatter with canonical source form;
- type/effect/profile checker;
- bytecode compiler/verifier and deterministic reference interpreter;
- language server with completion from the live capability registry;
- structured diagnostics with stable codes, primary/secondary byte spans, notes, safe fixes, and related capability/policy evidence;
- syntax grammar for editors and a generated GBNF for textual code;
- canonical typed AST JSON Schema for providers that support structured output;
- AST/RDF/CBOR-LD mappings generated from the same node definitions;
- documentation and the `SKILL.md` generated/versioned from the same language and registry source.

The golden corpus should include substantially more than happy paths:

- valid source -> AST -> bytecode -> state delta/receipt;
- invalid lexing, parsing, type, effect, profile, and authority cases;
- RDF nesting/reification and canonicalization cases;
- every runtime profile and optional-capability fallback;
- buffer/cardinality/gas/time/cancellation exhaustion;
- transaction rollback and concurrent CRDT conflict cases;
- reactive cycles, event ordering, retry, and idempotency;
- sensitivity leakage attempts across logs, model, extension, network, and legacy web;
- deterministic CPU replay and declared GPU tolerance checks;
- fuzz/property tests and parser/serializer differential tests;
- migration fixtures for each language, bytecode, AST ontology, and package version.

Agent-generated code must be validated and policy-checked before execution. Suggested fixes should never add authority or weaken a sensitivity gate automatically.

## 14. Recommended staged delivery plan

### Stage 0 — Freeze terminology and truth sources

- Decide `.10d` versus `.d10`, RDF 1.2 surface syntax, HMC v1/v2 scope, and what “Vibe v1” includes.
- Resolve the NQuin parity/sensitivity/tag public contract.
- Establish one universal capability descriptor and status vocabulary.
- Label all current/partial/experimental/planned claims in the documentation.

**Exit criterion:** no known contradiction between normative docs, grammar examples, ABI, format code, and runtime-profile registry.

### Stage 1 — Core grammar and semantic model

- Implement the lossless parser, AST, formatter, type/effect checker, diagnostics, modules/imports/prefixes, bounded control flow, and pure reference evaluator.
- Include only scalar/semantic values and pure functions initially.

**Exit criterion:** all examples and negative syntax/type tests are generated or validated from the normative source; deterministic interpreter tests pass on native and WASM.

### Stage 2 — Minimal Qualia profile

- Bind `Iri`/`Did`/`Hash`, safe Quins, read-only graph snapshots, bounded typed queries, RDF parse/serialize, SHACL validation, and selected logic verdicts.
- Generate bindings from descriptors.

**Exit criterion:** source -> bytecode -> bounded graph query/logic result is reproducible, profile-checked, and never exposes raw ABI overlays.

### Stage 3 — Transactions, reactivity, and authority

- Implement graph transactions, reactive dependency graph, event scheduler, capabilities/grants, sensitivity and deontic gates, receipts, cancellation, and pure HCF cells.
- Integrate separately signed Vibe modules with declarative QApps.

**Exit criterion:** rollback, replay, cycle, retry/idempotency, revocation, and leakage tests pass.

### Stage 4 — Async jobs and full capability families

- Add geometry/tensor/render, scientific/domain compute, inference, vision, audio, asset/storage, and transport adapters according to registry maturity/profile.
- Keep cold/heavy work behind job handles and receipts.

**Exit criterion:** every exposed operation has a descriptor, budget, authority policy, cancellation behavior, error schema, and evidence-linked status.

### Stage 5 — WASM component and extension ecosystem

- Generate WIT worlds, component adapters, signed manifests, sandbox policies, and legacy-web bridge contracts.
- Certify browser/native/mobile/edge profiles independently.

**Exit criterion:** unavailable imports fail at install/validation time; component and extension effects cannot exceed granted capabilities.

### Stage 6 — Agent and ecosystem conformance

- Publish the ontology, schemas, GBNF, language server, corpus, skill, package registry rules, compatibility suite, and reproducible release artifacts.

**Exit criterion:** independent implementations can parse, type-check, verify, and execute the conformance suite consistently.

## 16. Illustrative target style

This example is intentionally illustrative, not a proposed frozen syntax. It shows the missing concepts: modules, prefixes, declared capabilities, typed events, budgets, transactions, effects, and receipts.

```vibe
module clinic.alerts@0.1;

prefix clinic: <https://example.org/clinic/>;
prefix snomed: <http://snomed.info/id/>;

requires {
    graph.read(context: clinic:telemetry),
    graph.write(context: clinic:alerts),
    aura.validate(shape: clinic:EmergencyAlertShape),
    pulse.publish(topic: "clinic/alerts")
}

on pulse.message(message: pulse.Message<Telemetry>)
    budget(steps: 20_000, workspace: 64_KiB, output: 16_KiB)
    -> Result<Receipt<GraphCommit>, AlertError>
{
    let reading = message.payload;
    if reading.temperature <= 85.0_C {
        return Ok(receipt.no_change());
    }

    let alert = rdf.reify(
        (reading.sensor, clinic:emitsAlert, clinic:OverheatCondition),
        provenance: message.provenance,
    );

    let commit = transaction(snapshot: message.graph_revision) {
        graph.stage(alert);
        aura.require(alert, clinic:EmergencyAlertShape)?;
    }?;

    effect await pulse.publish("clinic/alerts", commit.public_summary())?;
    Ok(commit.receipt)
}
```

The actual syntax can be more concise, but its semantics must remain this explicit.

## 17. Acceptance criteria for claiming “advanced Qualia/Webizen scripting language”

VibeScript should not claim comprehensive Qualia support until:

1. The parser accepts every normative example and rejects every negative fixture.
2. Types/effects/profiles prevent unsupported or unauthorized calls before execution.
3. The public Quin API cannot create invalid parity, role overlays, tags, or sensitivity states.
4. Capability bindings are generated from honest implementation registries and carry maturity/evidence.
5. The same package has defined behavior across each declared runtime profile, or fails validation with a precise unsupported-capability error.
6. Pure/realtime hot paths meet zero-heap/budget tests; cold jobs meet workspace/cancellation limits.
7. Graph mutations are atomic, shape/governance checked, replayable, and receipted.
8. Model, vision, audio, clinical, financial, and other uncertain outputs remain provenance-bearing epistemic proposals.
9. HCF/QApp integration preserves the declarative trust boundary and does not grant ambient authority.
10. Source, AST graph, bytecode, package, HMC, Q42, P64, and 10D version/canonicalization/signature rules are testable.
11. RDF/SPARQL/SHACL/CBOR-LD claims name exact versions/profiles and pass published conformance tests.
12. Agent generation is followed by parser, type/effect, profile, budget, and policy validation, with no automatic authority expansion.

## 18. Final recommendation

VibeScript should move forward as a **typed, capability-secure semantic orchestration language** for Qualia/Webizen—not as an ever-growing list of branded built-ins and not as an alternative general-purpose browser language.

The full power of QualiaDB is too broad and fast-moving to encode directly in grammar. A small language plus a universal generated capability registry can expose the entire ecosystem while preserving profile honesty, safety, determinism, zero-heap hot paths, exactness, maturity, and future extensibility. The first engineering milestone should therefore be the shared semantic/type/effect/capability contract, followed by a parser-backed minimal graph/logic profile. Geometry, render, inference, vision, audio, scientific, networking, and domain packages can then arrive without destabilizing the core language.
